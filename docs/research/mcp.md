# Model Context Protocol: research notes for HyFib's hosted MCP server (ADR-416)

**Retrieval date:** 2026-10-21

**Method statement:** Every page below was fetched directly, as raw Markdown (MDX) or TypeScript,
from the official specification repository `modelcontextprotocol/modelcontextprotocol` on GitHub,
branch `main`, through `raw.githubusercontent.com`. The GitHub API for the repository was refused
by this environment's proxy, so the revision list comes from the repository's own site navigation
(`docs/docs.json`), which names "Version 2026-07-28 (latest)". The same pages are published at
`https://modelcontextprotocol.io/specification/<revision>/...`. Quotes are the specification's
words; anything else in a row is marked as our reading. The base of every URL below is
`https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/`, written as
`…/`.

Confidence levels:

- **High:** the specification's normative text (MUST, SHOULD, MAY) or its schema, read in full.
- **Medium:** our reading of how two revisions combine, or text the specification leaves open.
- **Low:** not in the specification; a convention or an observation of one tool.

| ID      | Topic                      | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Source URL                                                                                     | Confidence |

| MCP-006 | Message shapes and codes   | Requests: `{ jsonrpc: "2.0"; id: string \| number; method; params? }`; "Requests MUST include a string or integer ID"; "the ID MUST NOT be `null`". Results: same id, a `result` that "MUST include a `resultType` field" (2026-07-28). Errors: `{ jsonrpc, id?, error: { code, message, data? } }`; the id is left out only "where the ID could not be read due a malformed request". Notifications "MUST NOT include an ID" and get no response. Codes: JSON-RPC's -32700 and -32600 to -32603; -32000 to -32019 legacy, implementation-defined; -32020 to -32099 reserved for the specification ("Implementations MUST NOT emit any code from this sub-range that is not defined by this specification"); "New error codes for purposes not defined by this specification SHOULD be allocated outside the JSON-RPC reserved range (-32768 to -32000)". HyFib's transport refusals use the HTTP status (401, 403, 413, 415, 429, 400) as their code, which is outside that range, except a body that is not valid JSON, which is JSON-RPC's parse error -32700 (still HTTP 400); once the body was read, such an error carries the request's id when it can be read. | …/docs/specification/2026-07-28/basic/index.mdx ; …/schema/2026-07-28/schema.ts               | High       |
| MCP-007 | Per-request `_meta`        | Required on every modern request: `io.modelcontextprotocol/protocolVersion` (string) and `io.modelcontextprotocol/clientCapabilities` (object); optional `io.modelcontextprotocol/clientInfo`. "A request missing any required field is malformed; the server MUST reject it with JSON-RPC error code -32602 (Invalid params). On HTTP, the response status MUST be 400 Bad Request." Servers "SHOULD include … `io.modelcontextprotocol/serverInfo` in every result's `_meta`"; `Implementation` requires `name` and `version`. clientInfo and serverInfo are self-reported and "SHOULD NOT" be relied on "for security decisions".                                                                                                                         | …/docs/specification/2026-07-28/basic/index.mdx ; …/schema/2026-07-28/schema.ts               | High       |
| MCP-008 | `tools/list`, `tools/call` and errors | `tools/list` (`params.cursor?`) answers `{ resultType, tools, nextCursor?, ttlMs, cacheScope }` (modern; legacy has `tools` and `nextCursor?`). `tools/call` (`params.name`, `params.arguments?`) answers `CallToolResult { content: ContentBlock[], structuredContent?, isError? }`; text content is `{ "type": "text", "text": … }`. Two error mechanisms: **protocol errors** (unknown tool, a request failing the CallToolRequest schema, server errors) as JSON-RPC errors, the example being `-32602 "Unknown tool: invalid_tool_name"`; **tool execution errors** (API failures, input validation errors, business logic errors) "reported in tool results with `isError: true`". 2025-11-25 clarified that input validation errors are tool errors (SEP-1303); 2025-06-18's tools page lists "Invalid arguments" under protocol errors (and "Invalid input data" under tool errors). So HyFib answers arguments that fail a tool's schema with -32602 when the version is 2025-06-18, and as tool errors for 2025-11-25 and 2026-07-28; refusals of the service itself (scope, window, not found) are tool errors in every revision (our reading of "Business logic errors"). An invalid cursor is -32602.                                                                                | …/docs/specification/2026-07-28/server/tools.mdx ; …/docs/specification/2025-11-25/changelog.mdx ; …/docs/specification/2025-06-18/server/tools.mdx ; …/schema/2026-07-28/schema.ts | High       |
| MCP-009 | Tool definitions           | `Tool { name, title?, description?, inputSchema: { type: "object", … }, outputSchema?, annotations?, icons?, _meta? }`. Names "SHOULD be between 1 and 128 characters", of `A-Z a-z 0-9 _ - .`. `inputSchema` "MUST be a valid JSON Schema object"; without `$schema` it is JSON Schema 2020-12. `ToolAnnotations`: `title`, `readOnlyHint` (default false), `destructiveHint` (default true, meaningful only when not read-only), `idempotentHint` (default false), `openWorldHint` (default true); "clients MUST consider tool annotations to be untrusted unless they come from trusted servers". "Servers SHOULD return tools in a deterministic order". The list "MUST NOT vary per-connection" but "MAY vary by the authorization presented on the request". `CacheableResult`: `ttlMs` (milliseconds, ≥ 0) and `cacheScope` (`"public"` or `"private"`: "private" may be reused only within the same authorization context).                                                                                                                      | …/docs/specification/2026-07-28/server/tools.mdx ; …/schema/2026-07-28/schema.ts               | High       |

| MCP-010 | POST with `application/json`          | "Every JSON-RPC message sent from the client MUST be a new HTTP POST request to the MCP endpoint." The client "MUST include an Accept header listing both application/json and text/event-stream". For a notification the server "MUST return HTTP status code 202 Accepted with no body", or "an HTTP error status code (e.g., 400 Bad Request). The HTTP response body MAY comprise a JSON-RPC error response that has no id." For a request the server "MUST return either Content-Type: application/json (a single JSON object) or Content-Type: text/event-stream". A server answering only JSON is therefore conforming. The Accept rule binds the client; the specification does not ask the server to refuse a request without it, so HyFib does not (our reading). 2026-07-28 "defines no client-to-server notifications over Streamable HTTP"; 2025-11-25 also allows a POSTed JSON-RPC response, answered 202 if accepted.                                                         | …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx ; …/docs/specification/2025-11-25/basic/transports.mdx       | High       |
| MCP-011 | GET, DELETE and sessions              | 2026-07-28 has no GET stream and no sessions; a server of only that revision receiving older traffic "SHOULD respond … HTTP GET or DELETE to the MCP endpoint: respond with 405 Method Not Allowed. An `Mcp-Session-Id` header on a request: ignore it, and do not mint or echo session IDs." 2025-11-25: to a GET "the server MUST either return Content-Type: text/event-stream … or else return HTTP 405 Method Not Allowed"; "A server using the Streamable HTTP transport MAY assign a session ID" (sessions are optional); to a session DELETE "The server MAY respond … with HTTP 405 Method Not Allowed". So a stateless server answers GET and DELETE with 405 and never sends `Mcp-Session-Id` in either era.                                                                                                                                                                                                                                                                     | …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx ; …/docs/specification/2025-11-25/basic/transports.mdx       | High       |
| MCP-012 | The protocol version header           | 2026-07-28: "Every POST request to the MCP endpoint MUST include an `MCP-Protocol-Version` header", whose value "MUST match the `io.modelcontextprotocol/protocolVersion` field"; a mismatch is "400 Bad Request and a HeaderMismatch JSON-RPC error"; an unsupported version is "400 Bad Request and an UnsupportedProtocolVersionError"; an unimplemented method is "404 Not Found and a JSON-RPC error with code -32601". "A server that does not support such clients [earlier than 2025-06-18] MUST reject a request without the header per Server Validation." 2025-11-25: the header is sent on requests after initialization; without it, and with no other way to know, "the server SHOULD assume protocol version 2025-03-26"; "If the server receives a request with an invalid or unsupported MCP-Protocol-Version, it MUST respond with 400 Bad Request." HyFib keeps no session, so a legacy request without the header means 2025-03-26, which it does not serve: refused with 400 (-32020, as Server Validation names a missing header). | …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx ; …/docs/specification/2025-11-25/basic/transports.mdx       | High       |
| MCP-013 | `Mcp-Method`, `Mcp-Name`              | Required on every 2026-07-28 POST: `Mcp-Method` (from `method`, all requests) and `Mcp-Name` (from `params.name`, for `tools/call`, `resources/read`, `prompts/get`). A value that is not plain header-safe ASCII is sent as `=?base64?{Base64 of UTF-8}?=`, which "servers MUST decode … before comparing"; that encoding is defined for `Mcp-Name` and `Mcp-Param-{Name}` only, so HyFib compares `Mcp-Method` exactly and refuses a sentinel there as a mismatch. Servers "MUST reject requests where the values specified in the headers do not match the corresponding values in the request body" with 400 and -32020; failures include a missing required header and "A header value contains invalid characters". Header values are visible ASCII, space and tab. "header requirements for notification POSTs are not defined by this revision." `x-mcp-header` (parameters mirrored as `Mcp-Param-*`) is optional for servers; HyFib uses none.                                                                                                                                                                                                        | …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx                                                              | High       |
| MCP-014 | The Origin check                      | Both revisions: "Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks. If the Origin header is present and invalid, servers MUST respond with HTTP 403 Forbidden. The HTTP response body MAY comprise a JSON-RPC error response that has no id." The specification does not say which origins are valid. HyFib's choice (our reading, conservative): no Origin (MCP clients are not browsers) or exactly the app's own origin; anything else, `null` included, gets 403 before authentication, on every method.                                                                                                                                                                                                                                                                                                                                                                                                                       | …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx ; …/docs/specification/2025-11-25/basic/transports.mdx       | High       |
| MCP-015 | Batches                               | 2025-06-18's changelog: "Remove support for JSON-RPC batching". 2025-11-25: "The body of the POST request MUST be a single JSON-RPC request, notification, or response." 2026-07-28: "The body of the HTTP POST MUST be a single JSON-RPC request or notification." No revision HyFib serves requires batches, so an array body is refused (400, -32600). 2025-03-26 had batching per that changelog; it is not served.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | …/docs/specification/2025-06-18/changelog.mdx ; …/docs/specification/2025-11-25/basic/transports.mdx ; …/docs/specification/2026-07-28/basic/transports/streamable-http.mdx | High       |

| MCP-016 | Authorization                 | "Authorization is OPTIONAL for MCP implementations. When supported: Implementations using an HTTP-based transport SHOULD conform to this specification."
