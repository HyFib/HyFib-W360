# Meta WhatsApp Business Platform (Cloud API): research notes for a multi-tenant Tech Provider SaaS

**Retrieval date:** 2026-09-26

**Method statement:** The network egress policy blocked developers.facebook.com, so no official page could be fetched directly. business.whatsapp.com, facebook.com, docs.aws.amazon.com, 360dialog.com and ppc.land were blocked too. Unless a row says otherwise, claims come from search-index snippets of official pages. Those snippets pass through a search summarizer, so the wording is paraphrased and can lose context. **Re-verify every claim by fetching the page directly before production use.**

The session's shared web-search budget ran out after about 55 searches. The remaining gaps were filled from Meta-owned GitHub sources, which were fetched directly and are labelled below:

- **Meta OpenAPI spec:** `facebook/openapi`, file `business-messaging-api_v23.0.yaml`. The file name says v23.0, but its last commit is 2026-08-11 ("Document user_changed_user_id in webhook specs").
- **Meta Business SDKs:** `facebook/facebook-python-business-sdk` and `facebook/facebook-nodejs-business-sdk`.
- **Meta sample code:** `fbsamples/whatsapp-business-jaspers-market` (updated 2026-09-24) and `WhatsApp/WhatsApp-Flows-Tools`.

A few rows use third-party open-source code (pywa, `github.com/david-lev/pywa`). Those rows are marked third-party and should be treated as hints only.

## Implications for implementation

- **Pin one Graph API version in config** (v26.0 is current; v21.0 is removed 2027-01-21). Also set the app's webhook version deliberately, because payload fields differ between versions (M-009). Plan an upgrade roughly every year.
- **Embedded Signup:** implement v4 with `config_id`, `response_type: code` and `override_default_response_type: true`. Anything still on v2 must move before 2026-10-15. Exchange the code server-side within 30 seconds, and persist `waba_id`, `phone_number_id` and `business_id` from the session event. Treat both FINISH and closing the popup on the final screen as success.
- **Run onboarding as a resumable, idempotent job per tenant:** exchange the token, then `POST /{WABA_ID}/subscribed_apps`, then register the number with a PIN we generate and store securely (at most 10 attempts per 72 hours, and within 14 days), then check `health_status` and the payment method, then mark the tenant live.
- **Tech Provider model:** each customer adds its own payment method, and Meta bills the customer directly. Our platform fee must be billed separately. Plan for the default cap of 10 new customers per 7 days during launch.
- **Multi-tenant webhooks:** use one app-level endpoint and route by `entry[].id` (WABA) plus `metadata.phone_number_id`. Per-WABA or per-number overrides are possible, but template and account webhooks always hit the app URL.
- **Webhook ingestion:** verify `X-Hub-Signature-256` on the raw body, return 200 quickly, and do the work from a queue.
  - Deduplicate messages by WAMID and statuses by WAMID plus status.
  - Accept out-of-order and contradictory statuses (both delivered and failed can arrive).
  - Retries continue for up to 7 days.
  - Reconcile with `/{PHONE_NUMBER_ID}/message_history` where available.
- **Outbound sending:** there is no idempotency key, so use an outbox pattern with our own message IDs, and do not blindly retry on timeouts.
  - Rate-limit per phone number (80 mps by default) and per recipient (1 message per 6 seconds).
  - Back off on `130429` and `131056`.
  - Treat `131049` as "wait at least 24 hours" and `131047` as "window closed, a template is needed".
- **Customer service window:** track it per contact (24 hours from the user's last message or call), plus the 72-hour free entry point window, to decide between free-form and template messages and to predict cost.
- **Pricing:** handle the 2026-10-01 changes. Service messages above 1,000 per number per month become billable, and utility templates inside the window become billable. Record the `pricing` object from every status webhook for cost attribution, and reconcile with `/{WABA_ID}/pricing_analytics`.
- **Contact identity (BSUID):** key contacts on BSUID (`user_id`), with the phone number (`wa_id`) optional and possibly absent. Store `parent_user_id`. Handle `user_changed_user_id` and `user_changed_number` system messages. Offer `REQUEST_CONTACT_INFO` when a phone number is needed.
- **Inbound media:** download within the 7-day media-ID lifetime and re-fetch the URL each time (it is valid for 5 minutes). HyFib fetches a file each time a member opens it and keeps no copy (ADR-216); keeping files past WhatsApp's lifetime would need our own storage and retention policy.
- **Templates:** sync from the status, category and quality webhooks plus periodic `GET /{WABA_ID}/message_templates`. Handle PAUSED, DISABLED, ARCHIVED and recategorized templates. Upload header media via the Resumable Upload API.
- **Flows:** keep one RSA key per phone number, uploaded via `whatsapp_business_encryption`. Implement the `ping` health check and the 421, 427 and 432 responses. Monitor flow `health_status` and the BLOCKED and THROTTLED states.
- **Tokens:** store BISU tokens encrypted and per tenant, and check them periodically with `debug_token` (built: daily, ADR-137). Check that the app is still subscribed to each WABA's webhooks (built: the same daily check lists the subscribed apps and subscribes HyFib's app again when it is missing, ADR-138). Treat error 190 as possible deauthorization, since explicit signals are unconfirmed.

## Things we must NOT assume

- That service (non-template) messages or in-window utility templates are free after 2026-10-01.
- That a phone number (`wa_id`) is always present for a contact. BSUIDs can arrive without one.
- That webhooks arrive exactly once, in order, or with only one final status per message.
- That `/messages` supports an idempotency key, or that a timed-out send was not delivered.
